# Red Team（承重假设攻击）

日期：2026-08-27

## 攻击 1：差异化交互是「伪需求」还是「真痛点」？
- 攻击点：用户其实只想要「不打断地查词」，弹窗查词（蒙哥/欧路）已足够；「彩色虚线 + 小号字」是开发者的自我感动，增加视觉噪音、降低阅读沉浸。
- 证据现状：KOReader Offline Translate 已有「虚线淡下划线」先例，但无人系统化做「词性/难度/是否点击多维着色」——可能是「用户不需要」，而非「没人想到」。
- kill criteria：V1 访谈中多数用户认为「虚线+小字」比「高亮/弹窗」更吵或更难读；V3 留存不因标注功能提升。
- cheapest test：V1 三种呈现对比（1 周内，0 成本）。

## 攻击 2：Beachhead 人群太小或不愿付费
- 攻击点：「泛英语阅读爱好者」在手机上读英文原版书且愿付费的人本就少；开源 + BYOK 进一步抬高使用门槛（要会配 API key）。
- 证据现状：TAM/SAM/SOM 均「无结论」；竞品有付费先例但均为闭源、门槛更低。
- kill criteria：V2 waitlist 转化 <10% 且付费意向 <3%；或 MVP 内付费转化 <1% 且无付费意愿反馈。
- cheapest test：V2 落地页 + waitlist。

## 攻击 3：被竞品快速复制
- 攻击点：沉浸式翻译（20+ 引擎、多平台、2000 万用户）或 KOReader 插件一旦跟进「多分类虚线标注」，本产品护城河瞬间消失。
- 证据现状：沉浸式翻译重「译文对照」、KOReader 重「开源插件」，均未把「学习标注」作为主叙事，但跟进成本低。
- kill criteria：竞品在 3–6 个月内上线同形态标注功能。
- 缓解：本产品作为开源项目，差异化在「阅读器级深度集成 + 开源社区」，而非专利级功能。

## 攻击 4：BYOK 门槛杀死普通用户
- 攻击点：普通泛阅读者不会配置 API key；多模型可切换对小白是负担。
- 证据现状：沉浸式翻译免费版即支持自接 API，说明存在会自接的核心用户群，但比例未知。
- kill criteria：V3 中「完成 key 配置并成功使用翻译」的用户占比 <30%。
- 缓解：预设国内模型一键接入模板 + 极简引导；或提供「开发者内置 key 的付费档」作为备选（需用户决策）。

## 攻击 5：EPUB 划线的工程复杂度被低估
- 攻击点：跨平台 EPUB 渲染 + 单词级精准标注 + 长文性能，在个人兼职下可能做不出可用版本。
- kill criteria：8 周内无法产出「单词级标注不破排版」的 EPUB MVP。
- cheapest test：先用最小技术 spike（单平台、单 EPUB、词性+是否点击两档）验证可行性，再决定是否全量投入。

## Red Team 结论
最大风险是**攻击 1（伪需求）与攻击 4（BYOK 门槛）**，且两者都可用 1 周内的 cheap test（V1/V2）提前探知。建议：在写完整 App 前，先跑 V1（交互对比）+ V2（落地页 waitlist），通过后再投入 MVP 开发。
